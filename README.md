🗒️ 桌面便签 · 待办清单（Windows 悬浮小组件）
一款吸在屏幕边缘的 Windows 桌面便签：做完一件事打一个勾，平时自动收起只露一条彩色小把手，
鼠标滑到边缘（向下滑动）它就滑出来，悬浮在所有窗口之上。
启动
三种方式任选：
1. 安装版（推荐，启动最快）：双击安装版.exe，向导式安装，自动创建桌面 + 开始菜单快捷方式与开机自启。装好后直接运行已安装的程序（%LOCALAPPDATA%\Programs\便签\便签.exe），原地运行、不重复解压，启动明显快于便携版。
2. 便携版：双击便携版.exe，单文件免安装，可拷到任何 Windows 电脑。注意：便携版是自解压包，每次启动都会解压到临时目录再运行，且首次运行会被杀软扫描，因此启动比安装版慢。
3. 双击 启动便签.vbs（无黑窗）或 启动便签.bat：优先调用已安装的便签，找不到时回退到源码运行；命令行 npm start 亦可。
首次启动会看到一张示例便签，1~2 秒后自动收起到屏幕边缘，只留一条彩色小把手。
打开速度优化（已内置）
- 开机自启默认开启：登录即自动运行，需要用的时候便签早已就绪，"打开"几乎是瞬间的事。不想要可在右键菜单 →「开机自动启动」关掉。
- 开机自启不弹面板：从登录项启动时便签保持隐藏（只有右下角托盘常驻，不弹出便签面板），需要时再点托盘或滑到屏幕边缘唤出——避免一开机就被便签面板打扰。
- 优先用安装版：安装版程序常驻磁盘、原地启动，免去便携版每次自解压的开销。
- 首开较慢属正常：未签名的 exe 被移到新位置（如换盘/换目录）后，Windows Defender / Smart App Control 首次会做一次云信誉检查，首次打开可能多等几秒，之后会被缓存，后续打开就快了。

右键 / 托盘 → 「未完成任务提醒」开启后，每隔设定时间在 Windows 通知中心弹出尚未完成的事项（全部做完则不再打扰），点通知可直接唤出便签

右键 / 托盘 → 「提醒频率」子菜单可选：5 / 10 / 15 / 30 / 60 分钟，或「自定义…」输入任意分钟数（1–240）即时生效
🚪 关闭程序
右键 / 点 ⋯ → 「退出便签」，或托盘右键 → 退出
单窗口设计：所有待办都在同一个面板里，底部输入框直接添加，
不会再弹出任何新窗口；旧版本的多张便签会自动合并成一张，内容不丢。
收起状态：屏幕边缘会留一条 8px 的彩色把手（挂在屏幕顶部/底部/侧边），
鼠标进入它周围约 26px 的热区即滑出展开；移开鼠标 0.7 秒后自动收起。
更新系统（基于 GitHub，可选启用）
便签内置了一套零依赖的更新检查：它直接读取你 GitHub 仓库的 Releases（最新发布），发现新版本时在 Windows 通知中心提示，点击即可前往下载。无需自己维护 latest.json、无需代码签名。
一次性配置（仅首次）
1. 在 GitHub 新建一个公开仓库（例如 bianqian），把本项目代码推上去。
2. 打开 main.js，把顶部常量 GITHUB_REPO 设为 "你的用户名/仓库名"（例如 "Lemons0816/bianqian"）。
3. 重新打包（见下方「打包」）。
以后每次发布更新（只需 3 步）
1. 升版本号：把 package.json 的 version 改成新版本，例如 1.1.0。（必须有，否则便签会认为"已是最新"。）
2. 重新打包：npm run build，得到 便签-1.1.0-安装版.exe 和 便签-1.1.0-便携版.exe。
3. 在 GitHub 发 Release：
  - 打一个 tag，形如 v1.1.0（必须带 v 前缀，且版本号要与 package.json 一致）；
  - Release 标题随意，描述（Release notes）会作为更新通知的第一行文字；
  - 把两个 exe 作为 assets 上传。
发完即可。下一次用户启动便签（或点菜单「检查更新…」）时，就会自动检测到 v1.1.0 并弹通知，点击直达下载。
行为说明
- 启动 8 秒后静默检查：有新版才弹通知，无更新 / 失败都不打扰。
- 右键 / 托盘菜单「检查更新…」可手动检查：有更新直接打开下载直链，无更新弹"已是最新"。
- 菜单底部显示当前版本「便签 vX.Y.Z」。
- 仅在 GITHUB_REPO 非空时启用；留空则完全禁用、不打扰。
- 检测的是 GitHub 的 latest Release（自动排除草稿和预发布）。
⚠️ 重要：旧版本（≤ 1.0.0）必须手动升级一次
这是"先有鸡还是先有蛋"的问题，不是配置错误。
v1.0.0 及更早的版本内部用的是 旧的 UPDATE_URL + latest.json 方案，那时并未配置更新源；它们的代码里根本没有 GitHub 检查逻辑，因此不可能感知到新发布的 GitHub Release。
所以会看到这样的现象：
- 在旧版（≤ 1.0.0）上点「检查更新…」→ 弹「尚未配置更新源」并提示去填 UPDATE_URL。这是旧版代码的固有行为，你把 GITHUB_REPO 填得再对也没用——那个 exe 认都不认识这个常量。
- 即便 v1.1.0 已经在 GitHub 发布，旧客户端也看不见，不会自动推送。
结论：从 ≤1.0.0 升到具备 GitHub 更新能力的版本（如 1.1.0），这一次必须手动安装；从它之后起，往后就全自动了。
手动升级（一次性，约 1 分钟）：
1. 右键托盘图标 → 退出，确保旧便签已完全关闭（否则 exe 被占用无法覆盖安装）。
2. 下载安装版：https://github.com/Lemons0816/bianqian/releases/download/v1.1.0/bianqian-1.1.0-setup.exe
3. 覆盖安装即可。便签数据不会丢失——内容和设置存在 %APPDATA%\便签\notes.json（在用户目录，不在安装目录），安装程序不会触碰它，开机自启、提醒频率等设置也会保留。
4. 验证：托盘菜单底部应显示「便签 v1.1.0」；此时再点「检查更新…」会提示"已是最新版本"（因为已装 1.1.0 = GitHub 最新 1.1.0）。
顺带一提：GitHub Release 的资产上传建议用英文文件名（如 bianqian-1.1.0-setup.exe）。GitHub 的资产名编辑框对中文支持不佳，中文名资产常被塌缩成同名，导致发布时报 release assets name has already been taken。便签识别安装版的规则是"文件名含 setup/安装版 且不含 portable/便携版"，英文命名同样能被正确识别。
国内从 GitHub Release 下载可能偏慢。如需加速，可在 main.js 的 checkForUpdates 里把下载直链（asset.browser_download_url）的 https://github.com 替换为镜像前缀（如 https://ghproxy.com/https://github.com）；或自行改用对象存储托管安装包。
数据与设置
- 所有便签内容保存在：%APPDATA%\便签\notes.json（右键菜单里可直接打开）
- 托盘图标在屏幕右下角：左键点击 = 显示/收起，右键 = 菜单（自动隐藏 / 置顶 / 开机自启 / 退出）
- 单实例运行：重复启动只会把已有便签唤出

打包（可选）
npm run build
一次生成两个版本到 dist/：
- 便签便携版.exe —— 单文件免安装，可拷到任何 Windows 电脑直接运行
- 便签安装版.exe —— NSIS 向导安装，可选安装目录，自动创建桌面/开始菜单快捷方式
注意：每次改了版本号打包后，dist/ 里会同时存在新旧两个版本的 exe（旧的不会被自动删除）。分发或双击启动时务必认准当前版本号，误点旧 exe 会跑回老旧的更新逻辑（详见「更新系统」一节的说明）。建议打包后清理掉旧版本产物。
